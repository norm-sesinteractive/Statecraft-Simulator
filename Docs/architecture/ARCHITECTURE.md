# Architecture

> **Owns:** code organization, assemblies, patterns, conventions, determinism, and how the Unity side meets the
> simulation. **Budget:** 400 lines. **Read when:** writing or restructuring any code.

File-by-file listing: [../generated/CODEMAP.md](../generated/CODEMAP.md). Building, testing and automation:
[TOOLING.md](TOOLING.md).

## The one big rule: the simulation is pure C# (D-0006)

The model lives in `Statecraft.Sim`, an assembly with `noEngineReferences: true`, so a stray `using UnityEngine`
fails to compile. Unity renders the simulation and feeds it commands; it never is the simulation.

- **Testable:** a test plays 300 years in well under a second and asserts design intent.
- **Deterministic:** same seed and same commands give the same game (saves, replays, regression tests).
- **Portable:** the same sources build in Unity and under the .NET SDK (Tools/Headless, D-0007), so Claude can
  iterate on the model with the editor open.

## Simulation patterns

- **The Simulation owns everything.** `Simulation` holds the World, the random generator, the command queue,
  the ledger and the event log. No statics hold state; no singletons.
- **Systems in a fixed order.** Each internal `ISimSystem` runs once per tick in the order `Simulation` sets.
  The order is part of the model ([../simulation/MODEL.md](../simulation/MODEL.md)).
- **Commands in.** `SimCommand` subclasses are the only public way to mutate state. They queue and apply at the
  start of the next tick. Only the sim assembly can define them (the abstract `Apply` is internal).
- **Events out.** `EventLog` keeps recent `SimEvent`s plus a running total; views poll it after ticks rather than
  subscribing mid-tick. Events carry data, never text.
- **Read-only outside.** State exposes public getters over internal fields, so Game and UI cannot write sim
  state (the assembly boundary enforces it). Tests can, through InternalsVisibleTo.
- **Explain everything (D-0013).** Every additive term of a computed target goes through `Ledger.Add`. Sources
  that are quantities use `Ledger.NameOf` naming, so terms chain into a graph. A mechanic that skips the ledger
  is not finished.
- **Tuning in one place.** Every coefficient is a public field in `Tuning/*Tuning.cs` with an XML summary,
  which becomes its row in PARAMETERS.md. No magic numbers inside systems.
- **Scenarios are data.** A scenario is a list of `NationSetup` objects (`ScenarioLibrary`). [PLANNED] Load
  scenarios and tuning from data files; when that lands, the code defaults go, leaving one source of truth.
- **Equilibrium start.** `Simulation.Settle` starts the stocks at equilibrium for the starting levers.

## Determinism

- Randomness only from `SimRandom` (PCG32, seeded, state exposed for saves). Never `System.Random`, whose
  algorithm differs between runtimes, and never `UnityEngine.Random`.
- No wall-clock time, no dependence on `Dictionary` iteration order, no parallel systems.
- Same runtime, seed and commands give bit-identical results (tested). Mono (Unity) and .NET (headless) may
  differ in the last bits of `Math.Exp`, so across the two runtimes results agree statistically, not bitwise.

## C# constraints (Unity 6 compiles C# 9 against .NET Standard 2.1)

- No file-scoped namespaces, global usings, records, `init`, `required` or other C# 10+ features. The headless
  harness enforces this (LangVersion 9, implicit usings off, warnings as errors).
- Tests stick to NUnit 3.5 APIs (Unity's bundled version): no `Assert.Multiple`.
- Never give a type the same name as its namespace (`Scenarios.Scenarios` broke lookup; see LESSONS).

## Unity side

- **Composition root:** `GameRoot` (execution order -100) builds the `Simulation` and hands it to
  `SimulationHost`. It is the only place the game constructs sim objects.
- **Time:** `SimulationHost` is the only caller of `Simulation.Advance`. It turns unscaled real time into whole
  ticks (speeds of 0, 1, 2, 4 and 8 months per second), caps ticks per frame, pauses when the app goes to the
  background (mobile), and raises `Ticked` at most once per frame.
- **Views read; commands write.** Views (WorldView, DevHud) refresh on `Ticked`. Player input becomes
  `SimCommand`s via `SimulationHost.Enqueue`. Visuals run on `Time.deltaTime`; simulation time is ticks.
- **UI Toolkit (D-0008):** UXML for layout, USS for style, C# to bind. PanelSettings scales with the screen at a
  1920x1080 reference, matching height. `SafeAreaPadding` keeps content clear of notches. An EventSystem with
  the Input System UI module uses the package's shared default UI actions, as InsignificAnts does.
- **Scenes are generated (D-0009):** `MainSceneBuilder` builds Main.unity and its supporting assets;
  `ProjectSetup` applies player settings. Change the code, then run `Tools/unity.ps1 -Mode setup` (or the
  Statecraft menu in the editor).
- **Placeholder visuals:** primitives sharing one URP Lit material, tinted per object with MaterialPropertyBlocks.

## Mobile considerations

- Android first: IL2CPP, ARM64, minimum API 26; iOS bundle id set; landscape only (provisional, D-0017).
- Touch targets of at least about 72 px at the 1080 reference height; sizes in reference pixels, never device pixels.
- ASCII only in UI strings (device fonts lack symbol glyphs).
- No per-frame allocation in UI refresh paths (DevHud reuses its labels). The sim allocates nothing per tick
  after warm-up.

## Save and load [PLANNED M4]

Either a snapshot of sim state (levers, cohorts, stocks, alarms) with the RNG state and date, or the starting
scenario plus the command log for replays.

## Conventions

- Namespaces mirror folders: `Statecraft.Sim.Core`, `.Society`, `.Institutions`, `.Nations`, `.Systems`,
  `.Commands`, `.Tuning`, `.Diagnostics`, `.Scenarios`; then `Statecraft.Game`, `Statecraft.UI`, `Statecraft.Editor`.
- One public type per file, named after the type. An XML `<summary>` on every public type (feeds CODEMAP.md)
  and every tuning field (feeds PARAMETERS.md).
- Comments explain why, not what. Units and ranges go in names or summaries.
- A mechanic is finished when it has its code, ledger terms, tuning fields, a behavior test, and its section in
  MODEL.md.
